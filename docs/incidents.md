### 문서(4절)에서 **틀렸던 것** — 다음 세션은 이걸 믿지 마라

### 문서에 **없던 것** — PWA 때문에 새로 생긴 요구사항

- **`color-scheme: light`가 두 곳에 못박혀 있다**: `globals.css`(신규, PWA 검은화면 수정 때 들어옴)와

- **PWA standalone 상태바**: `manifest.ts`의 `theme_color`는 설치 시점에 박혀 런타임에 안 바뀐다.
  실제로 색을 따라가는 건 `<head>`의 `<meta name="theme-color">`이고, FOUC 스크립트와 `toggleTheme`이
  같이 갈아끼운다(`#d9cbff` ↔ `#0b0d19`). **Next의 `viewport.themeColor`로 옮기지 마라** — 그 export를
  두는 순간 기본 viewport meta가 안 나가고, 조건부 값은 `prefers-color-scheme`뿐이라 이 앱에선 못 쓴다.
- **iOS 스플래시/상태바는 범위에서 뺐다(사용자 승인).** iOS는 `theme-color`를 무시하고, 해법인

## 11-2. 🔴 이번 세션에서 실제로 시간을 태운 함정 3가지

문서 12절에 이미 비슷한 항목이 있지만, **다크모드에서 어떻게 나타나는지**가 달라서 따로 남긴다.

### (1) 특이도 역전 — "다크 규칙을 썼는데 연회색으로 남는다"

먼슬리메모 하단 목록과 프로젝트 목록이 계속 연회색이었다. 규칙이 없어서가 아니었다:

```
라이트  dialog.tonedown .memo-row      (0,2,1)   ← 이김
다크    [data-theme="dark"] .memo-row  (0,2,0)   ← 무시됨
```

두 다이얼로그가 **`glass-dialog big tonedown`**이라 그 안에서는 라이트가 이긴다. 파일 뒤쪽이어도
특이도가 낮으면 진다. 같은 유형이 `.proj-table` / `.memo-search` / `.proj-search` / taskList 체크박스까지
5건 있었다. **해법은 다크도 같은 컨테이너를 타서 (0,3,1)로 올리는 것.** `!important`는 쓰지 마라 —
라이트가 `!important`가 아니라 특이도만으로 충분하고, 뿌려두면 다음 사람이 아무것도 못 이긴다.

전수 검사 방법(다음에도 그대로 써라): 라이트/다크 규칙을 셀렉터별로 파싱해 **마지막 클래스 + 속성**이
같은 조합을 찾고, 라이트 특이도가 모든 다크 규칙보다 높으면 출력한다. 21건이 나왔고 그중 손대면
안 되는 것(`.big-postit.c6/.c7` 하위, `memo-compose-color-black` 하위)이 16건이었다 —
**검정/진회색 메모지는 라이트에서도 이미 어두운 카드라 밝은 글자를 쓴다. 덮으면 §5가 깨진다.**

### (2) 스캔 임계값이 대상을 통째로 누락시켰다

Phase 3 대상을 뽑을 때 "밝은 배경"을 **휘도 0.80 + 알파 0.55 이상**으로 걸렀다.
`.memo-row`는 `rgba(255,255,255,.45)`라 **알파 컷오프에 걸려 조용히 빠졌다.**
0.20으로 내려 다시 뽑아야 했다. 목록·개수는 손으로 세지 말라는 CLAUDE.md 규칙의 다른 얼굴이다 —
**뽑는 조건 자체가 틀리면 자동화도 똑같이 틀린다.**

### (3) `backdrop-filter`는 fixed 자식의 containing block을 만든다

상태 드롭다운을 포털로 빼고 `position: fixed` + 뷰포트 좌표로 띄웠더니 **웹에서만** 엉뚱한 곳에 떴다.
`dialog.glass-dialog`에 `backdrop-filter: blur(30px)`가 있어서 그 요소가 fixed의 기준이 된다.
실측: 다이얼로그가 (113,399)에 있으면 fixed의 (0,0)이 화면 (114,400)에 그려진다.
**모바일이 멀쩡했던 건 다이얼로그가 전체화면(0,0)이라 어긋남이 0이었기 때문**이고, 그래서
"모바일은 되는데 웹만 이상하다"로 보였다. → **host 기준 상대좌표 + `position: absolute`**로 해결.

포털에는 대가가 하나 더 있다: **조상 클래스에 의존하는 CSS가 전부 죽는다.**
이 경우 10개 규칙(`.proj-detail-editing .proj-filter-panel{width:98px !important}` 등)이 걸려 있었다.
→ 조상 클래스 체인을 **`display: contents` 래퍼**로 재현했다. 셀렉터 매칭에만 참여하고 상자는 안 만든다.
CSS를 10곳 고쳐 포털용 셀렉터를 덧붙이는 것보다 낫다(두 벌을 영원히 맞춰 써야 하므로).
폭은 인라인 `width` 대신 **`--anchor-w` 변수**로 넘겨야 한다 — 인라인 width는 더 구체적인 CSS 규칙까지
이겨버려서 모바일 크기를 깨뜨린다.

**(A) `-webkit-backdrop-filter`를 표준 속성과 같이 쓰면 빌드가 둘 다 버린다.**

```css
backdrop-filter: none !important;

```

파일에는 분명히 있는데 **브라우저 CSSOM에는 그 선언만 없다.** `.next`를 지우고 dev 서버를

서버를 두 번 재시작했다. **판별법:**

```js
// 규칙은 있는데 원하는 선언만 없으면 캐시가 아니라 빌드가 버린 것이다
[...document.styleSheets].flatMap(s=>{try{return [...s.cssRules]}catch(e){return []}})
  .filter(r=>r.selectorText&&/내-셀렉터/.test(r.selectorText)).map(r=>r.cssText)
```

접두 없이 `backdrop-filter`만 써라. 같은 파일의 다른 규칙들은 접두를 안 써서 멀쩡히 살아 있었다.

**(B) `backdrop-filter`는 배경색을 지워도 경계를 남긴다.**

사용자가 "포스트잇 경계"를 **세 번** 지적했고, 세 번째까지 못 잡은 이유가 이것이다.
`background`를 `transparent`로 만들어도 `backdrop-filter: blur(8px)`는 **자기 사각형만큼 뒤를
흐리게 그린다** — 색은 같은데 톤만 다른 판이 그대로 보인다.
**내 스캐너가 `backgroundColor`/`backgroundImage`만 봐서 "경계 없음"이라는 거짓 결론이 나왔다.**
→ 경계를 찾을 때는 `backdrop-filter`와 `box-shadow`, `outline`까지 같이 재라.

출처는 `7136` `[data-theme="dark"] [data-memo-theme="dark"] .big-postit .big-body-input`.

**의도적으로 안 고친 것** (다음 세션이 "버그"로 오해하지 마라):

### (1) 포스트잇 입력칸 경계 — 3라운드 (2026-08-24 ~ 25)

**증상**: "포스트잇 기본+전체메모 수정 시 입력칸 경계 있음. 하나의 포스트잇처럼 매끈하게."

**실제 원인은 세 겹이었다**:

| 겹 | 원인 | 어느 라운드에 잡혔나 |
|---|---|---|
| 1 | `.big-postit .rich-editor-content`의 경계 제거 규칙이 (0,2,0)이라 다크 색 규칙 (0,3,0)에 짐 | 1라운드 |
| 2 | 제목 밑줄·유형/날짜 칩은 **내가 고치지 않기로 판단**했다 | 2라운드 |
| 3 | `backdrop-filter: blur(8px)`가 배경과 **별개로** 경계를 그린다 | 3라운드 |

**왜 오래 걸렸나 — 세 가지 다 다른 이유다:**

- **1라운드→2라운드**: 내가 **스스로 범위를 좁혔다.** "제목 밑줄과 날짜 칩은 클릭 컨트롤이라 경계가
  필요하다"고 판단해 남겨두고, 그 판단을 보고서에 한 줄로만 적었다. 사용자가 지우라고 한 게 정확히
  그것들이었다. **사용자가 "다"라고 하면 범위를 좁히지 말고 다 하고 나서 되돌릴지 물어라.**
- **2라운드→3라운드**: **스캐너가 틀린 속성만 쟀다.** 경계를 찾는 스캐너가 `backgroundColor`와
  `backgroundImage`만 읽었다. `backdrop-filter`는 배경색이 아니라서 "경계 없음"이라는 **거짓 음성**이
  두 번 나왔고, 나는 그 측정을 근거로 "매끈해졌다"고 두 번 보고했다.
  → **경계를 찾을 때 재야 하는 것: `background*` + `backdrop-filter` + `box-shadow` + `outline` + `border`.**
- **3라운드 안에서 또 1시간**: `backdrop-filter: none !important`를 넣었는데 **안 먹었다.**
  `-webkit-backdrop-filter`를 같이 썼더니 **빌드(lightningcss)가 두 줄 다 버렸다.** 파일에는 있고
  CSSOM에는 없는 상태라 캐시 문제로 오진했고, `.next` 삭제 + dev 서버 재시작을 두 번 했다.
  → **판별법**: 규칙 자체는 CSSOM에 있는데 **특정 선언만** 없으면 캐시가 아니라 빌드가 버린 것이다.

**교훈 한 줄**: *측정 도구가 그 속성을 안 보면, 없는 게 아니라 안 보이는 것이다.*

### (4) 채용공고 수집 실패 — 5라운드, ✅ **원인 확정·수정 완료** (2026-08-25)

> **결론부터: 차단도 리전도 병렬화도 아니었다. `retryJobs`가 자동 경로용 시간 게이트에 막혀

### 진짜 원인 (한 문장)

`retryJobs`는 `daily_jobs_run` 행을 지우고 캐시까지 비우는 **"guard를 명시적으로 우회하는 유일한

는 못 넘었다. 사용자가 **새벽 1시 35분**에 눌렀으니 게이트가 정확히 false를 반환했고, 수집은
시작조차 안 됐다. → `getJobsForUser(..., { force: true })`로 수동 경로만 게이트를 우회한다.
남용 방지는 시계가 아니라 `manual-refresh-limit`(하루 상한)이 담당한다.

**왜 이 조합이 하필 지금 터졌나**: 버튼 노출 기준은 `MANUAL_REFRESH_MIN`(11:30)이고 수집 게이트는
`CRON_SCHEDULED_MIN`(10:10)이라 **정상 시간대에는 두 창이 안 겹친다.** 그런데 자정을 넘겨 열어둔
화면이나 10:10 이전 접속에서는 **버튼은 보이는데 눌러도 아무 일도 안 일어난다.** 사용자는 새벽에
작업 중이었다.

**그 다음 겹이 드러났고**, 매번 "이번엔 원인이 보이겠지"라고 생각했다.

```

  밝기 200 이상 픽셀        0.0%      ← 흰색이 존재하지 않는다
  불투명 픽셀 중 순수 검정  96.3%
  카드 내부(중앙 70%) 투명   23.0%    ← 글씨가 '구멍'이다
```

워드마크 "점핏."은 **검은 카드에 뚫린 구멍**이고, 뷰어가 그 투명을 흰색으로 렌더한 것이다.
알파 맵을 아스키로 찍으면 글씨 모양이 공백으로 그대로 드러난다(아래 절차 참고).

**따라서 글씨 색 = 박스 배경색이다.** 그래서:

| 박스 배경 | 글씨가 보이는 색 |
|---|---|
| 다크 기본 `rgba(255,255,255,.14)` | **회색** ← 사용자가 신고한 증상 |
| 내가 시도했던 `#0d0d0d` | **더 검정** ← "글씨가 더 까매졌다"는 그 보고 |
| 불투명 `#fff` | **흰색** ← 정답 |

내가 박스를 어둡게 한 수정은 **증상을 정확히 악화시켰고, 나는 왜인지 몰랐다.** 근거로 삼은 것이
(a) PNG를 눈으로 본 것 (b) 다른 로고 박스에 이미지만 바꿔 끼운 합성 비교 — **둘 다 틀린 측정**이었다.

#### 두 번째 원인 — CSS를 받을 클래스가 아예 안 붙어 있었다

`logoClass`가 JSX 삼항이었다: `j.source_site === "원티드" ? "wanted-logo" : undefined`.
점핏·잡코리아는 **클래스 자체가 없었다.** 뉴스 쪽은 `logoClass`를 아예 넘기지 않았다.
`dashboard.css`를 grep해도 `.jumpit-logo`가 안 나오니 "규칙이 없구나"까지만 알고,
"클래스가 안 붙는다"는 층은 못 봤다.

이제 `JOB_SITE_LOGOS` / `NEWS_SOURCE_LOGOS`가 `{src, cls}` 맵이다 — **단일 source of truth**.
로고를 추가하면 여기 `cls`를 넣어야 CSS가 붙는다.

2. 새벽 테스트를 막는 대신 크론이 갈아엎게 했다 — `clearPreCronBatches`가 `generated_at`이
   예약 시각(10:10)보다 이른 오늘 `daily_jobs_run` 행을 지운다.
3. 커밋·푸시·크론 실행. `jobsOverwritten: 2`, 배치 교체 확인, 관리자 화면 `정상 2/2`. **보고 완료.**
4. 다음 질문: **"채용공고 12시05분 마지막 업데이트인데 NEW 뱃지 없는거 정상인가?"** → 정상 아니었다.

**진짜 원인**

`daily_jobs_run`만 지웠고 **`saved_job`에 남은 삽입은 그대로 뒀다.** 새벽 배치가 찾은 신규 2건
(점핏 위시드·코어시큐리티)이 `saved_job`에 `first_recommended_date=오늘`로 박혀 있었고,

`frd`가 전부 과거라 NEW가 하나도 안 붙었다.

**`isNewBadge` 판정은 정확했다.** 신규가 실제로 없었던 것이다 — 내가 밀어냈기 때문에.

더 나쁜 것: 그 2건은 어느 배치에도 안 속한 **고아 row**로 남아 URL이 영구히 "본 것"으로
취급되어 다시는 추천되지 않는다.

**왜 실측 다섯 번이 전부 통과했나**

| 실측한 것 | 결과 | 놓친 것 |
|---|---|---|

| 크론 응답 | `jobsOverwritten:2` | 갈아엎기가 **완전한지**는 안 봤다 |

**전부 내가 지운 테이블 하나만 쟀다.** `daily_jobs_run`을 다섯 번 다른 각도로 확인하는 동안
`saved_job`은 한 번도 안 봤다. 화면에 뜨는 공고는 `saved_job`에서 나오는데.

**교훈 — 다음에 무엇을 다르게 할 것인가**

1. **🔴 상태를 되돌릴 때는 그 상태가 몇 개 테이블에 걸쳐 있는지 먼저 세라.**
   `assembleDailyJobs`는 `daily_jobs_run`과 `saved_job` **둘 다** 쓴다. 한쪽만 되돌리는 롤백은
   롤백이 아니라 **새로운 불일치 상태를 만드는 것**이다. 삭제 코드를 쓰기 전에
   `grep -n "from(\"" ` 로 그 함수가 건드리는 테이블을 전부 뽑아라.
2. **🔴 내가 바꾼 것을 재는 것은 검증이 아니다. 사용자가 보는 것을 재라.**
   사용자는 `daily_jobs_run`을 보지 않는다. **화면에 뜨는 4건과 그 배지**를 본다. 그걸 안 쟀다.
   (§CLAUDE.md 1번 "사용자 말과 내 측정이 어긋나면 틀린 쪽은 내 측정 범위"와 같은 실패다 —
   이번엔 사용자가 지적하기 **전에** 스스로 범위를 좁혔다.)
3. **🔴 내가 만든 관측 수단이 내 버그를 못 볼 수 있다.** 같은 세션에서 관리자 페이지 판정 로직을
   짜고 그걸로 자기 수정을 검증했다. `예약 전 생성` 사유는 잡도록 만들었지만 "신규 후보가
   배제됐다"는 잡을 이유가 없었다. **`Job 신규 ┌ 신규 N건 └ 재추천 N건` 줄이 이미 화면에 있었고
   거기 신규 0건이 떴을 것이다 — 나는 그 줄을 안 봤다.** 자기가 만든 계기판을 자기 검증에 쓸 때는
   "이 계기판이 이 버그를 볼 수 있는가"를 먼저 물어라.
4. **삭제 순서**: `saved_job` 먼저, `daily_jobs_run` 나중. 반대면 `saved_job` 삭제 실패 시
   guard만 사라져 같은 증상이 남는다.
5. **북마크는 배치와 무관하다.** 롤백에서 `is_bookmarked=true`는 제외한다(데이터 손실).

**고친 커밋**: `8f47499`. 대상 판정은 `created_at`이 `그날 KST 00:00 ~ 예약 시각` 구간인 row —
`saved_job` row는 `assembleDailyJobs`만 만들기 때문에 이 구간의 `created_at`이 곧 "예약 전 배치가
새로 삽입한 것"과 같다. 재추천 row는 `created_at`이 과거이고 `updated_at`만 갱신되므로 안 걸린다.

**미해결**: 이미 생긴 고아 row 4건(두 계정 각 2건)과 2026-08-25 배치는 **사용자가 직접 수동
업데이트로 처리**했다. 새 코드는 2026-08-26 크론부터 적용된다.

### (6) 🔴🔴 같은 세션에 두 번 — 지뢰 표에 적힌 지뢰를 내가 밟았다 (2026-08-25)

**사용자 반응: "씨.팔. 메모수정 앞으로/뒤로가기 하면 다시 그 좆같이 지옥같은 스크롤 막힘 현상
나오고 제대로 작동안됨 .. 아 진짜 PTSD온다 ㄹㅇ로"** — 그리고 이어서 **"핸드오프랑 노션 버그지뢰밭만
봐도 씨발 좀 나올텐데?"**. 맞는 말이었다. 답이 §3 지뢰 표 안에 이미 있었다.

#### 무슨 일이었나

undo/redo가 작동하지 않는다는 지적을 받고 `chain().focus().undo().run()`을 이렇게 바꿨다:

```ts
const ok = editor.commands.undo();
if (ok) editor.commands.focus();   // ← 여기
```

`focus()`의 기본값은 `{ scrollIntoView: true }`다(`@tiptap/core` d.ts에 그대로 적혀 있다).
`MemoRichEditor`에는 이미 캐럿 노출의 **유일한** 소유자가 있는데(`vv.resize`가 멈춘 뒤 한 번
`scrollIntoView()`) 거기에 **두 번째 스크롤 주체**를 만든 것이다. §3 지뢰 표의 이 줄이 정확히
그것을 금지한다:

> **캐럿 노출의 소유자는 정확히 하나** … **여기에 스크롤을 더 넣지 말 것**

5라운드 포스트모템까지 써둔 그 증상을 내 손으로 되살렸다.

#### 왜 밟았나 — 지뢰 표를 안 읽은 게 아니다, **내 diff와 연결하지 않았다**

이 세션에서 §3 표를 이미 여러 번 인용했다(로고 건, 반쪽 롤백 건). 그런데 undo/redo를 고칠 때는
"에디터 명령 문제"로만 봤고 **"이 수정이 스크롤을 건드리는가"를 묻지 않았다.** 지뢰 표는 증상별로
정리돼 있어서, 내가 지금 만지는 API가 그 증상과 연결된다는 걸 **스스로 이어야** 쓸모가 있다.

**다음부터: 에디터·스크롤·포커스·viewport를 건드리는 수정은 §3 표에서 그 단어들이 들어간 줄을
grep해서 먼저 읽는다.** `grep -n "스크롤\|포커스\|캐럿" CLAUDE.md` 한 줄이면 된다.

#### 고친 것

```ts
if (ok && !editor.isFocused) editor.commands.focus(undefined, { scrollIntoView: false });
```

포커스만 되돌리고 스크롤은 건드리지 않는다. 버튼 쪽 `onPointerDown` `preventDefault`가 포커스를
지켜주므로 대개 이 호출조차 필요 없다.

**검증(실제 로그인 세션, 375px, 다크)**: undo `edLen 2464→1499`, redo `1499→2464` 둘 다 작동,
`.textarea-row`가 `overflowY:auto / overflowX:hidden`로 scrollable 유지, undo/redo 후 수동 스크롤이
`257→377`로 정상 이동 — 스크롤 막힘 없음.

#### 같은 세션의 다른 발견들 (전부 실측으로 원인 확정)

| 증상 | 진짜 원인 |
|---|---|
| "현재 커서 위치에 삽입"을 2~3번 눌러야 됨 | `setPendingInsert(null)`이 `await recordMemoSource(...)` **뒤**에 있어 1~2초간 버튼이 남았다. 클릭 1회로 이미 삽입됐는데 사용자는 안 눌렸다고 보고 다시 눌러 **중복 삽입**됐다. 실측: 수정 전 500ms에도 bar 잔존 → 수정 후 **120ms**에 사라짐 |
| 드래그 선택한 문장만 삽입 안 됨 | `insertContent`는 **문자열을 HTML로 파싱**한다. 전체저장(html)은 정상이지만 평문은 `<`가 태그로 먹히거나 개행이 사라져 아무 일도 안 난 것처럼 보였다. `insertTextAtCursor(content, isHtml)`로 갈라 평문은 text 노드 + hardBreak로 넣는다 |
| 메모로 복사 창에 상단 액션 줄이 없음 | 그 블록이 포스트잇 상세 편집에만 있었다. `memoHeadActions(ref)`로 뽑아 두 곳에서 쓴다 |
| 삽입 버튼이 눌려도 반응 없음 | 삽입 대상 ref 후보가 둘뿐이었다(에디터는 **네 곳**). 후보에 없는 창이 떠 있으면 `target.current`가 null이라 `?.`에서 **조용히** 끝났다 |
| 다크에서 "메모로 저장" 시 라이트 메모지 | `bigEditorNode`의 `.postit-overlay`에 `data-memo-theme`이 없었다 — 다크 메모지 팔레트 **CSS 규칙 150개 전부**가 이 속성에 걸려 있다 |
| 도움말 줄바꿈이 엉망 | ① `word-break`가 기본값이라 한국어가 **단어 중간에서** 끊겼다("확인할 수 있습니/다") ② 소스 문구의 하드코딩 `
`(데스크톱 폭 기준)을 `white-space: pre-line`이 좁은 폭에서 그대로 그렸다. 문구 243곳을 고치는 게 아니라 CSS 두 줄이 답이었다 |
| 뒤로가기(‹)와 탭이 안 맞음 | 실측 ‹ 중심 23 vs 탭 중심 34. `top`에 고정 px를 주면 폰트를 키울 때마다 또 어긋나므로 head 안쪽 높이를 `top~bottom`으로 채웠다. **한 번 무력화됐다** — `height: auto`에 `!important`를 안 붙여 뒤의 `height: 40px !important`에 졌다(§3 "!important가 조용히 무력화한다") |

#### 이 세션에서 새로 배운 환경 함정

- **dev 서버가 옛 코드를 본다.** HMR websocket이 자주 죽어서(`ws://.../_next/hmr ... failed`)
  이미 고친 정규식의 파싱 에러를 계속 봤다. **`next build`는 통과하는데 dev만 실패하면 캐시다** —
  서버 재시작 + `.next` 삭제. CSS는 별도 파일이라 HMR 없이 반영될 수 있어 **JSX는 옛것, CSS는 새것**인
  어긋난 상태가 나온다(그 탓에 "상단 툴바는 뜨는데 `data-memo-theme`은 없다"는 이상한 조합을 봤다).
- **"Encountered a script tag while rendering React component"는 dev 전용이다.** 그 문구가
  `react-dom`의 `.development.js`에만 있고 production 번들에는 없다. 공식 경로는
  `next/script` + `strategy="beforeInteractive"`(인라인은 `id` 필수)지만, 그건 컴포넌트 위치와
  무관하게 head에 주입되므로 `querySelector`로 다른 meta를 찾는 스크립트라면 **순서 의존을 없애야** 한다.
- **CSS 여러 줄 주석을 붙여넣을 때 `*/`가 중간에 끼면 본문이 CSS로 노출된다.** `tsc`는 CSS를 안 보므로
  그대로 통과한다. `/*`·`*/` 개수와 "주석 밖 텍스트 노출"을 매번 검사했다(652/652 → 659/659).
- **`getComputedStyle`의 `backgroundImage`를 앞부분만 잘라 보면 오독한다.** 다크 메모지는 2레이어이고
  둘째가 노란 유리다 — 첫 레이어만 보고 "반투명 흰색"이라 읽어 한 라운드를 헛짚었다.

### (7) 🔴🔴 undo/redo 3라운드 · 삽입 5라운드 — **원인은 둘 다 "ref가 안 보이는 사본을 가리켰다"였다** (2026-08-25)

사용자 지적: "3번째 포스트잇 메모 뒤로가기/앞으로가기 제대로 안됨", "메모수정 앞으로/뒤로가기 하면
다시 그 스크롤 막힘 현상", "드래그 선택이 삽입 안됨 5번째".

앞선 두 세션은 **명령(command) 층**만 고쳤다 — chain 분리, `focus(..., {scrollIntoView:false})`.
둘 다 맞는 수정이었지만 증상이 안 사라진 이유는 **버튼이 부른 ref가 애초에 딴 에디터**였기 때문이다.

#### 실측으로 잡은 진짜 원인 두 개

1. **`postitViewNode`가 3벌 마운트돼 있었고 셋이 `detailEditorRef` 하나를 공유했다.**
   `<dialog>`는 닫혀 있어도 자식이 살아 있으므로 Monthly MEMO / Key Notes / postitOnly 세 곳의
   포스트잇이 전부 마운트 상태였고, React ref는 **마지막 마운트가 이긴다** → 화면에 안 보이는
   사본이 ref를 가져갔다. 그 에디터는 히스토리도 캐럿도 비어 있다.
   - 실측: `.postit-overlay.open .textarea-row` 3개, clientHeight `[648, 0, 0]`
   - undo 클릭 → 본문 길이 `3593` 그대로, 콘솔 `[memo] 실행 취소할 내용이 없다`
   - 1563절 주석이 이미 규칙을 적어뒀다("열려 있는 다이얼로그 key 안에서만 렌더링") — 그런데
     `bigEditorNode`에만 적용돼 있었다. 규칙이 없어서가 아니라 **한 노드에 안 붙여서** 났다.
   - 수정: `postitHostDialogKey`(= `activeDialogKey`, 단 `bodyEditor`면 `preBodyEditorDialogKeyRef`)로
     세 자리 전부 게이트. `Dashboard.tsx` 3379절 / 4665 / 4723 / 5492.

2. **prosemirror의 `undo`/`redo`가 자기 트랜잭션에 `scrollIntoView()`를 붙인다.**
   `editor.commands.undo()` → `@tiptap/extensions`의 UndoRedo → `prosemirror-history`의
   `undo = buildCommand(false, /* scroll */ true)`(`dist/index.js:408, 424~430`).
   즉 `focus()`의 스크롤을 껐어도 **스크롤 주체가 하나 더 남아 있었다** — 그게 "스크롤 막힘" 재발이다.
   수정: `undoNoScroll`/`redoNoScroll`을 직접 호출(`MemoRichEditor.tsx`).

3. (같이) `insertTextAtCursor`가 아직 `chain().focus().insertContent(...)`였다. 지뢰표의
   "chain은 한 덩어리다"가 undo/redo에만 적용돼 있었고 삽입 경로엔 그대로 남아 있었다 —
   모바일에서 버튼 탭 → 에디터 blur → 프로그래매틱 focus 실패 → **insertContent까지 통째로 무효**.
   이게 "2~3번 쳐눌러야 된다"의 나머지 절반이다. `editor.commands.insertContent()`로 먼저 확정하고
   포커스는 뒤에서 스크롤 없이. 삽입 버튼에도 `onPointerDown preventDefault`를 붙여 blur 자체를 막았다.

| 항목 | 수치 |

| 포스트잇 마운트 수 | 3 → **1** (`.postit-overlay.open`) |

### (9) 🔴🔴 "스크롤 잠김" 신고 대부분은 **앱 최상위 `.sp-body` 하나**로 수렴했다 (2026-08-26)

사용자가 같은 날 올린 신고 넷 중 둘이 같은 지뢰였다 — **지뢰표 첫 줄**(`overflow` 한 축만 쓰면 반대 축이 승격된다).

| 신고 | 실측 | 원인 |
|---|---|---|
| "메모 스크롤 잠김 — 뒤로/앞으로가기 **할 것이 없으면** 걸린다" | `.sp-body` **scrollHeight 2639 == clientHeight 2639**, `overflow-y`가 `auto`로 승격 | `.sp-body { overflow-x: hidden }` 한 줄. **메모·프로젝트·모든 다이얼로그가 이 밑**이라 전역으로 터졌다 |
| "채용공고 상세가 **한 문장만** 스크롤되고 막힘" | `.job-tabs` **scrollHeight 38 / clientHeight 37** — 1px 스크롤러 | `.job-tabs { overflow-x: auto }` 한 줄. 기본 규칙이 이미 `flex-wrap: wrap`이라 가로로 넘칠 일이 없어 **세로축만 승격**시켰다 |

#### 고친 방법 — `hidden`이 아니라 `clip`

```css
/* 안 된다: hidden은 반대 축을 auto로 승격시킨다 */
.sp-body { overflow-x: hidden; }
/* 된다: clip은 승격시키지 않는다 (Safari 16+) */
.sp-body { overflow-x: hidden; overflow-x: clip; overflow-y: visible; }
```

- 세로 스크롤러엔 `overflow-x: hidden`을 **같이** 적는다(`.textarea-row`가 원래 그 모양이다).
- 가로 스트립엔 `overflow-y: hidden`을 같이 적는다(`.cal-scroll-shell`).
- 이번에 한 축만 있던 규칙 **15개**를 전부 양축 명시로 바꿨다(dialog-inner 계열, copy-picker, proj-detail-inner, keynote-rest-grid, support/mypage/idea 패널 등).

#### 점검 프로브 — 손으로 세지 말 것

```javascript
// 반드시 **다이얼로그를 열어둔 상태**에서 돌려라. 결과가 0이어야 한다.
[...document.querySelectorAll('*')].filter(e=>{
  const c=getComputedStyle(e), sy=/auto|scroll/.test(c.overflowY), sx=/auto|scroll/.test(c.overflowX);
  return (sy && e.scrollHeight-e.clientHeight<=2) || (sx && e.scrollWidth-e.clientWidth<=2);
}).map(e=>e.className)
```

**수정 후 실측**: 메모 편집창 조상 체인에 스크롤러 **1개**(`.textarea-row`), Job/Memo/Project 다이얼로그 phantom **0개**,
`.sp-body`는 `overflow-x: clip / overflow-y: visible`. 빈 히스토리에서 undo/redo를 눌러도 `.textarea-row` 스크롤 300→300 유지(잠김 없음).

#### 같이 고친 것

- **프로젝트 상태 동그라미 3개**: 바깥 42px / 안 30px인데 여백이 좌 1 · 우 11 · 위아래 6이었다(동심원이 아님). 데스크톱은 아이콘·라벨·개수를 늘어놓는 flex 행이라 `flex-start`가 맞지만, 모바일은 라벨을 `display:none`하고 `padding:0`으로 바꿔놓고 `justify-content`를 안 줘서 안쪽 원이 왼쪽에 붙었다. → `justify-content: center` (수정 후 6/6/6/6).
- **도움말 News 문구**의 하드코딩 개행 위치를 사용자가 지정한 자리("필요한" 뒤)로 옮겼다.

#### 미해결 / 주의

- **"할 것이 없으면 잠김"의 인과는 데스크톱 Chrome에서 재현되지 않았다.** 구조적 원인(`.sp-body`)을 제거했을 뿐이라 실기기 확인이 필요하다. 재발하면 위 프로브를 **실기기에서** 돌릴 방법부터 만들어라(추측으로 값 조정 금지).
- `overflow: clip`은 Safari 16+다. 그 이하에선 앞의 `hidden` 폴백이 남지만, lightningcss가 두 줄을 합치면 폴백이 사라질 수 있다(지뢰표 "빌드가 선언을 버린다").
- 커밋 `c426ff6`.

### 왜 또 못 잡았나 — 실패 원인 7가지

#### ① 🔴🔴 증상 하나에 원인 하나를 가정했다 (가장 큰 실수)

"스크롤 잠김"은 **손끝의 감각**이다. 그 감각을 만드는 경로는 최소 다섯이다:

```
(a) 조상에 굴릴 수 없는 스크롤러가 있다        → iOS가 거기서 터치를 멈춘다
(b) 캐럿 노출 소유자가 둘이라 서로 다툰다        → 스크롤이 되돌려진다
(c) ref가 안 보이는 에디터를 가리킨다            → 명령이 조용히 아무 일도 안 한다
(d) --kb-inset이 죽어 편집창이 키보드 뒤로 늘어난다 → iOS가 화면을 밀고, 손가락은 그 밀림을 상대한다
(e) 스크롤 도중에 스크롤러 높이가 바뀐다         → 애니메이션이 멈춘 채 남는다
```

나는 매번 하나를 찾고 **"원인을 찾았다"**고 썼다. 정확히는 **"원인 하나를 찾았다"**였다.

> **다음부터:** 스크롤 신고를 받으면 다섯 경로를 **전부** 점검하고 결과를 표로 보고한다.
> 하나를 고쳤으면 **"(a)를 고쳤다. (b)~(e)는 이렇게 확인했다"**까지 써야 보고가 끝난 것이다.

#### ② 🔴🔴 6라운드 동안 잘못된 화면 크기로 쟀다

실기기는 `innerH=684`, 키보드가 올라오면 보이는 높이 **358**. **이 숫자는 `useViewportHeight.ts` 주석과 이 문서에 이미 적혀 있었다.**
그런데 나는 브라우저 기본 mobile 프리셋 **812**로 계속 쟀다. 812에서는 여유가 100px 넘게 남아 **잘림이 재현되지 않는다.**

글씨 크기 드롭다운이 그 증거다:

```
812px 뷰포트 + 키보드 326  → 메뉴 197..387,  스크롤러 103..481  → 여유 94px  → "정상"
684px 뷰포트 + 키보드 326  → 메뉴 197..387,  스크롤러 103..353  → 34px 잘림  → 재현
```

같은 코드, 같은 조작, 결론만 반대. **"재현 안 됨"의 절반은 화면 크기 때문이었다.**

> **다음부터:** 모바일 신고는 **무조건** `resize_window(375, 684)`로 시작한다. 812는 이 프로젝트에서 쓰면 안 되는 값이다.

#### ③ 🔴🔴 키보드 문제인데 키보드를 담당하는 파일을 5라운드까지 안 열었다

증상 설명에 "타이핑", "수정 중", "키보드"가 계속 나왔는데도 나는 `Dashboard.tsx`와 `dashboard.css`만 뒤졌다.
`src/lib/useViewportHeight.ts` — **`--kb-inset`을 계산하는 유일한 파일** — 을 처음 연 게 5라운드였고, 열자마자 결함이 나왔다.

> **다음부터:** 증상에 등장하는 **명사**를 파일 이름으로 바꿔 먼저 연다.
> 키보드 → `useViewportHeight.ts` / 스크롤러 → `.textarea-row`·`.dialog-body-scroll` 규칙 / 실행취소 → `MemoRichEditor` handle.

#### ④ 🔴 "재현 안 됨"을 결론으로 썼다

프로젝트 메모 스크롤을 한 라운드 통째로 **"재현하지 못했습니다"**로 넘겼다.
정답은 1분이면 나왔다 — **잘 돌아가는 형제 화면과 비교**하는 것:

```bash
grep -n "kb-inset" src/app/dashboard.css
# → 껍데기 3개 중 .proj-detail-inner만 안 나온다. 끝.
```

> **다음부터:** "재현 안 됨"은 결론이 아니라 **측정 방법을 바꾸라는 신호**다.
> 같은 일을 하는 화면이 여럿이면 **셋 다 나란히 놓고 CSS를 비교**한다. 하나만 규격에서 빠져 있는 경우가 실제로 있었다.

#### ⑤ 🔴 사용자가 **누른 것**과 증상을 연결했다 (상태가 아니라)

사용자가 "뒤로/앞으로가기 하면 잠긴다", "할 것이 없으면 잠긴다"고 했다. 나는 그 말을 그대로 받아 **undo/redo 명령 층만 세 라운드** 고쳤다.
실제로는 그 버튼이 **방아쇠**였고, 잠금은 그 전부터 있었다(⑴ 포커스가 옮겨간 순간 baseline이 오염됨 ⑵ 조상에 유령 스크롤러가 있음).

> **다음부터:** "X를 누르면 Y가 된다"를 받으면 **X를 누르기 전에 이미 Y였는지** 먼저 잰다.
> `할 것이 있으면 되고 없으면 안 된다` 같은 말은 **X가 부작용으로 리플로우를 일으켰다**는 신호다.

#### ⑥ 🔴 내 수정이 사용자 화면에 존재하지 않았다

여러 라운드 동안 수정이 **전부 uncommitted**였고, 사용자는 **배포된 설치형 PWA**를 보고 있었다.
"고쳤다 → 안 고쳐졌다"가 반복된 이유의 일부가 이것이다. 물어보는 데 10초 걸렸고, 나는 안 물었다.

> **다음부터:** 모바일/PWA 신고를 받으면 **첫 질문**이 "로컬 dev / 배포 / 설치형 PWA 중 어디서 보시나요"다.
> 배포면 **고치자마자 푸시**하고, 그 커밋 해시를 보고에 적는다.

#### ⑦ 🔴 내가 바꾼 것을 재고 검증했다고 했다

`querySelector`(단수)로 **내가 예상한 요소 둘만** 비교해놓고 "도움말 뒤로가기 고쳤다"고 보고했다.
진범(✕ 버튼)은 후보에 넣지도 않았다 — 두 규칙을 **읽고도** 특이도 순위를 반대로 매겼기 때문이다.

> **다음부터:** "겹쳐 보인다"는 예상 요소를 재는 게 아니라 `dialog[open] *` **전체**에서 rect가 겹치는 것을 뽑는다.
> `!important`끼리는 **특이도가 정한다** — 규칙을 눈으로 읽고 순위를 매기지 말고 **computed 값을 읽어라.**

> **`grep -n "kb-inset"`은 "규칙이 있나"만 답한다. "그 규칙이 이기고 있나"는 답하지 않는다.**
> 껍데기 점검은 grep이 아니라 **computed `padding-bottom`을 실측**해야 한다:
> ```javascript
> // --kb-inset:326px + html.kb-open 주입 후, 편집창을 열고
> getComputedStyle(shell).paddingBottom   // "326px" 계열이어야 한다. "28px"면 진 것이다.
> ```
> 그리고 `:has(.cal-grid)`처럼 **화면에 안 보이는 요소로도 매치되는 셀렉터**를 조심하라 —
> compose 중에 달력은 `display:none`일 뿐 DOM에 그대로 있어서 그 규칙이 계속 이긴다.

#### E. 🔴🔴 메인 화면 스크롤이 통째로 죽는다 — `<dialog>`가 우리 `close()`를 안 거치고 닫힐 때

`<dialog>`는 **Esc·안드로이드 하드웨어 뒤로가기·OS의 top layer 정리**로도 닫힌다. 그 경로에서는
`activeDialogKey`가 그대로 남아 배경 스크롤 잠금 effect의 cleanup이 **영원히 안 돈다** —
`body`가 `position: fixed; top: -Ypx; overflow: hidden`인 채로 굳는다.
body의 `overflow: hidden`은 뷰포트로 전파되므로 **문서 스크롤이 죽고**, 본문은 `top: -Y` 위치에서 잘린다.

```javascript
// prod 375x684, 1200px 스크롤한 상태에서 Monthly MEMO를 열고 Esc로 닫음
수정 전  scrollHeight 2644 → 684 | body position fixed | top -1200px | scrollTo(0,99999) 후 scrollY 0
수정 후  scrollHeight 2644       | body position static | top 없음     | scrollY 1200 복원, 바닥 1960
```

`onCancel`을 단 다이얼로그(Monthly MEMO / Key Notes)도 **조건이 안 맞으면 그대로 native close로 간다**
(`memoFormOpen`이 false일 때 등). 그래서 다이얼로그마다 `onClose`를 다는 대신 **`close` 이벤트를
document에서 캡처 단계로 한 번에 받는다** — `close`는 버블링하지 않지만 캡처는 target까지 내려온다.
`setActiveDialogKey(cur => cur === key ? null : cur)`로 가드를 둔 이유: `close()` 직후 다른 dialog를
`open()`하는 경로(`expandPostitView` / `closePostitView`)가 있는데 `close` 이벤트는 **비동기로** 오므로
그때는 이미 새 key가 들어가 있다. 가드가 없으면 방금 연 창의 잠금을 풀어버린다.

> **이게 "메인페이지 무한스크롤"의 유력한 정체다.** iOS는 `overflow: hidden`으로 배경 스크롤이 안 막히는
> 브라우저라(이 파일이 애초에 `position: fixed`를 쓰는 이유), body가 out-of-flow인 채 2644px을 그리는
> 상태에서 손가락을 대면 스크롤 범위 계산이 어긋난다. 다만 **실기기에서 "무한"인지는 확인 못 했다** —
> 여기서 확인한 것은 "문서 스크롤이 죽고 본문이 -1200px에서 잘린다"까지다.

#### F. 🔴 "메모 뒤로가기 렉" — ‹ 하나에 서버 왕복 2~3번 + 하드코딩 520ms 대기가 걸려 있었다

세 back 핸들러가 전부 **저장이 끝난 뒤에야** UI를 닫고 있었다. `CLAUDE.md` 지뢰표
"UI를 닫는 setState를 서버 왕복 뒤에 두지 마라"가 정확히 이 얘기인데 back 경로엔 적용이 안 돼 있었다.

| 핸들러 | 닫기 전에 기다리던 것 |
|---|---|
| `handlePostitBack` | `await updateMemo` + `await refreshAfterMemoChange`(그 안에서 또 1~2왕복) |
| `handleMemoDialogBack` | 위와 같음 **+ `await new Promise(r => setTimeout(r, 520))`** ("저장됨 ✓"를 보여주려던 대기) |
| `handleProjectDetailBack` | `await saveProjectIdea` |

```javascript
// prod, localhost(=네트워크 지연 거의 0)에서 포스트잇 ‹ 클릭

fetch-end    456ms      (updateMemo)
fetch-start  467ms → fetch-end 720ms   (refreshAfterMemoChange)
```

> ⚠️ **트레이드오프(사용자 판단 필요)**: 저장이 백그라운드로 가므로, 닫은 직후 앱을 완전히 종료하면

#### G. 💀 위로가기 — 캐럿을 옮겼다가 **더 나쁜 버그를 심고 같은 날 되돌렸다**

> **아래 내용은 실패 기록으로 남긴다. 이 처방을 다시 쓰지 마라.**

원래 처방(되돌림): `removeAllRanges()` → `addRange()`로 캐럿을 에디터 맨 앞에 옮긴 뒤 스크롤.
데스크톱에서는 완벽히 동작했다(실측 아래). **배포하자 사용자 신고가 돌아왔다:**

> "위로가기 눌렀을 때 **간헐적으로 메모수정 커서가 없어지고 "보기모드"로 돌입.**
>  그러면서 **메모내용이랑 키보드사이 간격** 갑자기 발생. 원래 괜찮다가." (프로젝트 포함)

**원인**: `removeAllRanges()`와 `addRange()` 사이에 **선택 범위가 0개가 되는 순간**이 있다.
iOS는 그걸 "캐럿이 사라졌다"로 보고 키보드를 닫는다. 그 다음은 전부 연쇄다 —
편집이 풀리고(`.postit-overlay`의 onClick이 detail 편집 중의 탭을 `setPostitEditMode(null)`로 받는다),
`--kb-inset`이 326→0으로 떨어져 껍데기 padding이 줄고, 다시 탭해 키보드를 올리면 baseline이 어긋나
본문과 키보드 사이에 죽은 공간이 생긴다(지뢰표 "focusout에서 baseline을 갱신하지 마라" 줄).

**데스크톱 Chrome에서는 재현되지 않는다.** 그래서 "실측 완료"로 보고했고 배포 후에 드러났다 —
이 문서 맨 위 "한 줄 요약"이 말하는 그 실패를 또 했다.

**지금 남아 있는 것**: `behavior: "smooth"` → `"auto"` 하나뿐이다. 부작용이 없는 쪽으로만 한 칸
움직인 것이지 증상을 고쳤다는 뜻이 아니다. 근거는 실측이다 — smooth는 **420ms 동안 900에서 멈춰
있다가** 0으로 간다(375×684 프로젝트 편집). 지뢰표 마지막 줄이 경고하는 리플로우 창이 정확히
거기다. 즉시 이동은 그 창이 아예 없고, 포커스·캐럿·편집 모드를 건드리지 않는다.

**"커서가 살아 있으면 안 올라간다"는 아직 원인 미확정이다.** 다음 라운드는 값을 만지지 말고
실기기 `?debug=vp`로 KB-INSET / vvTop / 스크롤러 목록부터 읽어라(CLAUDE.md 7절 4단계).

## 11-10. 2026-08-26 — "위로가기 안 먹힘" 10라운드 (회귀였다)

2. **목록이 있으니 재보지 않고 골랐다.** 지뢰 표에서 제일 비슷한 걸 갖다 붙였다.
3. **못 재는 상태에서 "재현 안 됨"을 결론으로 썼다**(패널 숨김 → rAF 6900ms에 1회).
4. **매 라운드 진짜 버그를 고쳐서** 진전된 느낌이 들어 멈추지 못했다. 진짜 버그 ≠ 사용자 버그.
5. **1라운드에 정답 근처까지 갔다가 스스로 지웠다.** "리렌더가 범인?" → "prosemirror가 스크롤
   복원은 안 하네" → 리렌더를 **통째로** 용의선상에서 뺐다. **속성 재작성은 한다**를 안 봤다.
   → **용의자를 알리바이 하나로 풀어주지 마라. 그 용의자가 할 수 있는 일을 전부 세라.**

## 11-11. 모바일 메모 편집창 "죽은 여백" — 2주, 상쇄 코드가 한 번도 실행되지 않았다 (2026-08-27)

**원인 1줄:** iOS 화면 밀기 상쇄 규칙 `.big-postit { transform: translateY(var(--vv-push)) }`(`ae6d744`)에
`!important`가 없어서 `transform: none !important`(dashboard.css 5288절, 포스트잇 기울임 제거용)와
`.postit.c1~c7 { transform: rotate(...) }`(0,2,0)에 져서 **한 번도 적용되지 않았다.**

**실측 (iPhone Chrome + 네이버 키보드, 684px 화면, `?debug=vp`)**

| | 값 | 뜻 |
|---|---|---|
| 껍데기 `top` | **-89** | 상쇄가 정확히 0. 밀린 양과 부호까지 완전히 일치 |
| `vvTop` | **89** | iOS가 민 양 |
| 스크롤러 아랫변 vs 키보드 상단 | **251 vs 341** | 죽은 여백 90px |
| `--kb-inset` | 343 (정상) | 패딩 계산은 처음부터 맞았다 |

수정 후 기대값: 껍데기 top 0 / 341 vs 341. **← 실기기 미검증(아래 참고).**

**왜 2주가 걸렸나 — 값을 의심하고 승자를 안 쟀다**

- `-89 / vvTop 89`는 "부호가 반대"가 아니라 **"아무 일도 안 일어났다"**는 값인데, 부호 문제로 읽고
  `translateY` 방향을 재검토했다. 상쇄가 0이면 먼저 **선언이 적용됐는지**를 묻는 게 맞았다.
- 두 실측이 서로 모순돼 보였다: `dashboard.css` 3005절은 "`offsetTop`을 더하면 이중으로 밀린다"고,
  `useViewportHeight` 주석은 "`+offsetTop`이 맞다"고 적혀 있었다. 부호를 정하는 데 라운드를 태웠는데
  **둘 다 부호 얘기였고 진짜 문제는 부호가 아니었다.** (3005절의 (1)은 오진이었다 — 그 시도는
  높이를 `--app-vh`로 **같이** 줄였고, 실제로 깬 것은 (2) "높이를 줄이면 아래 띠로 배경이 비친다"였다.
  두 변경을 한 번에 해서 (2)의 실패가 (1) 탓으로 기록됐다. 해당 주석은 근거와 함께 교정했다.)
- **진단 패널에 `--vv-push`가 없었다.** 그래서 "push가 0인가(JS) / push는 맞는데 껍데기가 안
  움직이는가(CSS)"를 **2주간 구분할 수 없었다.** 두 원인이 화면에서 완전히 똑같이 보인다.
- 패널이 `SCALE`을 `toFixed(2)`로 찍고 있었다 — `vv.scale`이 1.0000001이어도 `"1.00"`으로 보인다.
  `1 === vv.scale` 엄격 비교가 push를 0으로 만드는 **두 번째 경로**였고, 그 경로가 살아 있는지조차
  화면으로는 알 수 없었다.

**고친 것**

1. `dashboard.css` 맨 끝 상쇄 규칙에 `!important`. 5288절과 특이도가 같고 파일에서 더 뒤라 이긴다.
   기울임 제거 의도는 유지된다(`translateY`에 rotate 성분이 없다).
2. `useViewportHeight`: `vv.scale === 1` → `Math.abs(vv.scale - 1) < 0.01`(`notZoomed()`).
   소수를 갖는 값에 엄격 동등비교를 쓰고 있었다 — `vv.height`가 357.5인 것과 같은 이유다.
3. `ViewportDebug`: `VV-PUSH=` 행 추가(밀렸는데 push=0이면 경고 표시), `SCALE`은 raw 출력.
   **다음에 이 증상이 나면 이 한 줄로 JS/CSS가 갈린다.**
4. `dashboard.css` 3005절 오진 주석 교정(위 참고).

**검증 못 한 것**

- **실기기 미검증.** 데스크톱에는 키보드가 없어 `vv.offsetTop > 0`을 만들 수 없고, 이 사고의 본체가
  바로 그 경로다. 확인은 `?debug=vp`에서 `VV-PUSH=89px` + `껍데기 top 0` 두 값을 같이 보는 것이다.
- `.dialog-inner`(작성 폼) / `.proj-detail-inner.proj-detail-editing`(프로젝트)에서도 상쇄가 지고
  있었는지는 **안 쟀다.** 이 둘은 `transform: none !important` 목록에 없어서 원래 이기고 있었을
  가능성이 크지만, `!important`를 붙인 지금은 셋 다 확실히 이긴다.
- `notZoomed()` 완화가 실제로 필요했는지는 모른다 — CSS가 막고 있어서 push 값 자체를 한 번도
  관측하지 못했다. push=0의 **두 경로 중 하나를 닫은 것**이고, 남은 하나가 범인이었는지는
  이제 패널의 `VV-PUSH=` 행이 답한다.

### 11-11 추가 (같은 날) — 진짜 원인은 승격이었다. WebKit #191204

`!important`를 붙여도 실측은 `껍데기 top -9 / vvTop 9`, `348 vs 358`였다. **상쇄가 여전히 정확히 0.**
같은 증상을 세 번째 고치는 자리였고, 사용자가 두 번 "레퍼런스를 찾아라"고 했는데 나는 계속 재고 있었다.
검색 한 번에 원인이 나왔다.

**원인 (WebKit 버그 #191204, [dev.to 해설](https://dev.to/deanliu/the-ios-safari-keyboard-scroll-bug-fixed-with-one-line-of-css-1353))**

> 키보드가 올라올 때 **내부 스크롤러에 굴릴 것이 없으면** iOS는 캐럿을 보이려고
> **문서 자체를 스크롤하는 쪽으로 승격**한다. 그것이 `vv.offsetTop > 0`이다.

즉 `vv.offsetTop`은 고쳐야 할 대상이 아니라 **증상**이었다. 그래서 되돌리기(`scrollTo`)도
상쇄(`translateY`)도 통하지 않았다 — 둘 다 이미 일어난 승격을 사후에 상대하려 했다.

**이 프로젝트가 그 조건을 스스로 만들고 있었다**

- `dashboard.css` 4430절: 본문 박스를 `flex: 1 0 auto`로 두어 "짧으면 스크롤러를 딱 채운다"
  = `scrollHeight == clientHeight` = **굴릴 것 없음**.
- 글 끝~키보드 여백을 24 → 4 → 2 → **0**까지 깎았다(사용자 요청). 여유 0이 방아쇠다.
- 그래서 신고가 **"5~9줄만"**, 그 뒤 **"상단·중앙·후반 제각각"**이었다 — 캐럿 위치에 따라
  여유가 남는 경우에만 정상이었던 것이다. CLAUDE.md는 그 밴드를 "키보드가 새로 가리는 구간"으로
  설명했는데, 관찰은 맞았지만 **원인 해석이 틀렸다.**

**고친 것** — `dashboard.css` 맨 끝, `html:not(.kb-open)`일 때만 스크롤러 안쪽
(`.rich-editor-body-wrap`, 편집 영역 **밖**)에 `padding-bottom: 60vh`. 편집 껍데기 셋 전부.

`kb-open` **이후에는** 여유를 걷는다 — 그때는 `--kb-inset`이 키보드 몫을 이미 비워 스크롤러가
키보드 위에 완전히 들어와 있고, 여유를 남기면 4430절이 없앤 "글 끝에 빈 칸이 한참 이어진다"가
돌아온다. **여유가 필요한 구간(키보드 올라오는 중)과 거슬리는 구간(타이핑 중)은 겹치지 않는다.**

**불변식 ⑦ 추가** — `키보드 전 스크롤 여유 있음`(`kbInset === 0`일 때만 `scrollerSlack > 0`).
이게 있었으면 첫 라운드에 잡혔다. 패널의 "불변식 6개" 하드코딩도 `judge()` 길이로 바꿨다
(늘린 뒤 틀린 값으로 남아 있었다).

**검증 못 한 것**

- **실기기 미검증.** 데스크톱엔 키보드가 없어 승격 자체를 만들 수 없다.
- **`--vv-push` 상쇄를 남겨뒀다.** 승격이 사라지면 `vvTop=0`이라 `translateY(0)`으로 무해해지지만,
  승격이 남는 경로가 있으면 두 기전이 겹친다. 승격이 0으로 확인되면 **`--vv-push`를 통째로
  지우는 게 맞다**(그러면 `notZoomed()`·`scrollTo(0,0)`도 같이 지워진다).
- 60vh가 충분한지 안 쟀다. 근거는 "실측 키보드 343 / 화면 684 = 50vh"이고 60vh는 그 위 여유다.
  모자라면 `VV-PUSH`가 다시 0이 아닌 값을 갖는다 — 패널에서 바로 보인다.
- 사용자가 준 마지막 실측에 `VV-PUSH=` 행이 없었다. **옛 빌드를 보고 있었을 가능성이 있다** —
  다음 실측에서 그 행이 보이는지부터 확인해야 한다.

### 11-11 추가 2 — `inset > 0` 가드가 "밀리는 그 순간"에 상쇄를 끄고 있었다

60vh 여유를 넣어도 안 고쳐졌다. 사용자가 준 단서는 **"수정모드로 진입할 때"**였고 그게 답이었다.

`--vv-push` 계산에 `inset > 0` 가드가 붙어 있었다. 진입 순서를 따라가면 상쇄가 죽는 구간이 보인다:

| | 이벤트 | `inset` | `push` |
|---|---|---|---|
| ① | 본문 탭 → `focusin` | 0 (키보드 아직 안 올라옴) | 0 |
| ② | **iOS가 화면을 민다** → `vv.scroll` | **0** (`vv.resize`가 아직 안 왔다) | **0** ← 여기서 상쇄해야 하는데 꺼진다 |
| ③ | `vv.resize` | 343 | offsetTop — 이미 늦었다 |

②가 핵심이다. `inset`은 `baseline - vv.height`이고, iOS의 밀기는 `vv.height`가 줄기 **전에**
`vv.scroll`로 먼저 온다. 그 순간 `inset`이 0이라 가드가 상쇄를 통째로 건너뛴다.

**그리고 이 가드는 원래 아무것도 더하지 않는다** — 밀리지 않았으면 `offsetTop`이 0이라 `push`도 0이다.
안전장치가 아니라 실패 구간을 하나 만드는 코드였다. 제거했다(zoom 가드만 남긴다).

이게 세 번의 실측이 전부 `여백 == vvTop`으로 똑같이 나온 이유이기도 하다 —
`46 == 45`, `90 == 89`, `10 == 9`. **상쇄가 한 번도 안 붙었다는 뜻이다.**

**검증 못 한 것:** 실기기 미검증. `?debug=vp`의 `VV-PUSH=` 행이 이제 답한다 —
밀린 상태에서 `VV-PUSH=`가 `vvTop`과 같은 값이면 상쇄가 붙은 것이고, `0px`이면 남은 범인은
`notZoomed()`뿐이다(그 경우 `SCALE` raw 값을 보면 바로 안다).

**이것도 안 되면 값 조정을 멈추고 구조를 바꿔야 한다** — 껍데기를 `100dvh`(684) + `--kb-inset`
padding이 아니라 **시각 뷰포트 크기 그대로**(`height: var(--app-vh)`, `translateY(vv.offsetTop)`)로
잡는 것. 그러면 죽은 여백이 **구조적으로 불가능**해진다(껍데기 아랫변 == 보이는 아랫변).
3005절이 한때 시도했다 되돌린 방향인데, 그때 실패 이유는 "높이를 줄이면 아래 띠로 배경이 비친다"였고
그건 `.postit-overlay`만 `inset: 0`으로 남기면 해결된다. 삭제되는 코드가 많다:
`--kb-inset` padding 3곳, baseline 추적, 스파이크 클램프, `--vv-push`, `notZoomed`, `scrollTo(0,0)`.
